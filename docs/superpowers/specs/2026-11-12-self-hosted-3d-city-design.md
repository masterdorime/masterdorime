# Self-Hosted 3D Contribution City — Design

**Date:** 2026-11-12
**Status:** Approved
**Supersedes:** the third-party `yoshi389111/github-profile-3d-contrib` action

## Problem

The profile README shows two contribution totals that contradict each other.
The `CONTRIBUTION CITY` frame reads from our own snapshot and says **530**.
Directly beneath it, `profile-3d-contrib/profile-gitblock.svg` — generated by a
third-party GitHub Action — says **396**.

Both figures are honest for their own definition, which is exactly the problem.
The action fetches its own data with its own counting rule and its own window
(`2025-10-19 → 2026-10-24`), takes no input from us, and cannot be made to agree
with our snapshot. It also omits languages our snapshot includes (C# 12%,
Rust 7%), publishes nine variants we never reference, and contributes ~1.3 MB to
a repository whose whole purpose is to render a README.

**Goal:** replace it with a city we generate ourselves from the same snapshot
the other six widgets use, so every number on the page agrees by construction.

## Decision summary

| Question | Decision |
|---|---|
| Data source | The existing `data/profile-data.json` snapshot — one source for the whole page |
| Scope | One city, dark green/aurora. Not the nine variants |
| Old assets | Delete `profile-3d-contrib/` and `profile-3d.yml`, in a revertable commit |
| Width | 820px natural, matching the six widgets and the README column |
| Fit strategy | Shrink the cube step so all 53 weeks fit inside 820px |
| Empty days | Render as a flat dim floor tile, forming the ground plane |
| Colour ramp | Teal → cyan for levels 1–4, staying in the aurora family |
| Labels | City plus minimal labels (total, range, active days) |
| The frame | Stays as a separate panel directly above the city |
| Sequence | After the six widgets are finished and the README is wired |
| Review | Commit, then show the render |

## The geometry model

Decoded by inspecting the existing asset, not inferred. An isometric cube is one
group holding three `<rect>`s:

```
<g transform="translate(x y)">
  <rect width="18" height="18"    transform="skewY(-30) skewX(40.89) scale(1 1.15)"/>  top
  <rect width="18" height="{h}"   transform="skewY(30) scale(1 1.15)"/>                 left
  <rect width="18" height="{h}"   transform="translate(18 10.39) skewY(-30) scale(1 1.15)"/>  right
</g>
```

- The **top face** is flat; the **left and right faces** carry the height `h`.
- `h` is the skyline: it grows with the day's contribution count, so a heavy day
  becomes a taller tower. This is the effect that makes the graphic read as a
  city rather than a grid.
- The original grid steps **20px per week** horizontally and **11.55px per
  day-row** vertically. The isometric skew makes a 53×7 grid drift diagonally,
  which is why the original measures 59 distinct x and 94 distinct y values
  across 371 cubes.
- A year of 53 weeks at 20px is ~1060px, wider than our 820px column. The step
  therefore shrinks to fit. The exact step is computed from the panel width, not
  hard-coded, so the whole year is always visible in one block.

**The fit constraint, stated so it cannot be got wrong:** the grid is 53
week-columns wide, and the cube's own footprint is 18px at the original scale.
The horizontal advance per week is therefore
`min(20, (PANEL_W - 2*PAD) / 53)`, which at 820px with 30px padding is ~14.3px.
Every other dimension scales by the same factor `step / 20` — cube size, the
11.55px vertical row step, and the 10.39px right-face offset — so the cube keeps
its proportions and the isometric angle is unchanged. Nothing about the shape
depends on the panel width; only its scale does.

The panel height follows from the grid rather than being chosen:
`7 rows * rowStep * scale + top margin + label band`, so the city can never be
clipped and there is no dead space when the year is short.

## Colour

The original's `profile-night-green` ramp is RGB green with a grey level 0. The
rebuilt ramp moves to the aurora palette so the city reads as part of the same
page as the six widgets:

| level | meaning | role |
|---|---|---|
| 0 | no contributions | flat dim slate — a floor tile, not data |
| 1 | low | dim teal |
| 2 | moderate | mid teal |
| 3 | high | bright teal |
| 4 | highest | cyan |

Each level carries distinct top / left / right shades, preserving the 3D
lighting the original had. Level 0 stays deliberately low-contrast so empty days
recede and the active skyline is what the eye lands on.

Panel background is `#080e16`, matching every other widget.

## Architecture

```
widgets-pipeline/
  lib/iso.js                 NEW  pure geometry: grid -> cube rects, level -> shades
  renderers/city3d.js        NEW  grid layout + labels -> widgets/city-3d.svg
  renderers/city.js          existing  the frame panel (unchanged)
  fetch-data.js              MODIFIED  also record per-day counts
widgets/city-3d.svg          NEW  generated, committed
widgets/city.svg             existing  the frame panel
```

**Why `iso.js` is separate:** cube geometry is pure maths with no knowledge of
GitHub, the snapshot, or the panel. Isolating it means it is unit-testable
without rendering anything, and a layout change cannot accidentally alter the
shading model.

### Snapshot change

The current snapshot stores only aggregates (`total`, `activeDays`,
`busiestDay`). Drawing a skyline needs the **daily series**, so `contributions`
gains:

```jsonc
"days": [ { "date": "2025-11-09", "count": 0 }, ... ]   // 366 entries, calendar order
```

This is additive — the six existing renderers read `total`, `activeDays` and
`busiestDay`, which are unchanged. `contributions.days` is the only new field.

## Data flow

```
fetch-data.js  ->  data/profile-data.json  ->  city3d.js  ->  widgets/city-3d.svg
                        (one source)
                     ->  city.js (frame)   ->  widgets/city.svg
                     ->  the other five widgets
```

Every number on the page derives from the same snapshot, so the frame and the
city can no longer disagree. The frame supplies the aggregate; the city draws
the daily detail that produces it.

## Error handling

- A missing or empty `days` array renders an empty floor rather than throwing:
  an honest empty city beats a broken image.
- A day count that exceeds the top level is clamped to level 4, not scaled — the
  ramp is bounded and a new personal record should not silently redraw every
  other cube.
- The renderer is pure, so it cannot fail on a network condition. The fetch
  layer already refuses to overwrite a good snapshot on partial failure.

## Removal

Deleted in their own commit, so one `git revert` restores the previous city:

- `.github/workflows/profile-3d.yml` and the malformed duplicate at
  `.github/workflows/.github/workflows/profile-3d.yml`
- `profile-3d-contrib/` (nine variants, ~1.3 MB)

Once the new city is wired into the README, the old Action stops running and the
widget Action becomes the single scheduled job.

## Testing

`lib/iso.js`:
- the three faces of a cube are emitted for every grid position
- height increases monotonically with contribution level
- level 0 is height-flat (a floor tile, not a tower)
- levels above the maximum clamp to the top level
- the shade for a given level is stable

`renderers/city3d.js`, against the frozen fixture:
- self-contained: no `<script>`, no `on*=` handlers, no external `href`/`src`
- panel width is exactly 820
- the number of active cubes equals the number of active days
- **the sum of the rendered day counts equals `snapshot.contributions.total`** —
  the regression test for the defect that started this work
- an empty `days` array still produces a valid panel
- `<desc>` is derived from the rendered data, never hand-written

## Success criteria

1. The frame and the city show the same contribution total.
2. No `gitskins.com`, `yoshi389111`, or `profile-3d-contrib` reference remains.
3. The city renders as an image at 820px with legible cubes and correct chrome.
4. The whole page derives from one snapshot and is refreshed by one workflow.
5. Personal information and every untouched asset are unchanged.
